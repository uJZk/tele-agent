# 传输与会话层

```
exec / telefs / 变更推送 / MCP 代理 / 端口转发
   │ 多路复用流（yamux）
┌──▼─────────────────────────────────────────────┐
│ 会话层：session_id，每个方向的 seq/ack，重放缓冲 │ ← 重连后续传，上层无感
└──┬─────────────────────────────────────────────┘
   │ SS2022 流 ×N（交互、元数据、大块数据分别走不同的连接）
  TCP
```

## SS2022

- 库：[database64128/shadowsocks-go](https://github.com/database64128/shadowsocks-go)，方法 `2022-blake3-aes-256-gcm`。
- 目标地址固定为一个内部名称（`tele.internal:1`），这是两端之间的约定，tele 不做通用代理。
- SS2022 自带时间戳和 salt 重放过滤，所以**两端时钟误差必须在 30 秒以内**。`tele server install` 检查 NTP，`tele host ls` 和 `tele doctor` 报告时钟偏差。
- 未认证的连接按 RejectPolicy 处理：一直读到超时再关闭，不回任何字节，以抵抗主动探测。同时处于这种状态的连接数有上限，超过上限的立即关闭，免得探测耗尽文件描述符。
- 客户端无法区分 PSK 错误、时钟偏差超限和对端不是 tele server：三种情况下服务端都一言不发。所以客户端在收到第一个字节之前出错时，错误信息同时列出这三种可能。
- 「全随机字节流」在部分审查环境中会被识别。shadowsocks-go 的请求前缀功能可以用来伪装，作为可选的缓解手段。

## 可恢复会话层

TCP 连接一断，里面的所有流都会立即失效，所以在 SS2022 之上、业务之下需要一层可恢复的会话层（思路与 mosh、Eternal Terminal、QUIC 连接迁移相同）。

1. **会话身份与续传**：首次连接时客户端选定会话密钥，服务端分配 `session_id`；密钥只在加密的传输上传送一次。重连时服务端发一个随机挑战，客户端用会话密钥对它做 HMAC 来证明身份，只知道 `session_id` 不能接管会话。会话层承载的是一条字节流：双方各自记录已收到的字节数，定期确认，发送方保留对方尚未确认的字节；重连的握手中双方交换各自已收到的字节数，再从对方的数字处重发，所以每个字节**恰好送达一次**、次序不变，上层的流（包括 MCP 的长连接 stdio）完全无感。发送的字节一交给传输就计为已发送：对方的确认可能比写调用先返回。
2. **快速检测断线**：应用层心跳（间隔和判定阈值是代码中的常量）。同时监听本机 netlink 的链路、地址和路由变化（切换 Wi-Fi、IP 变化），不需要特权；一串变化合并成一次（去抖），然后**立即行动**，不等 TCP 超时：正在重拨的连接跳过退避马上再拨，看似正常的连接按下一条迁移，因为旧连接可能绑在已经消失的地址上，要等很久才会报错。netlink 的接收缓冲区溢出（`ENOBUFS`）也当作一次变化。
3. **先建后断**：网络变化时，或者对方沉默超过两个心跳间隔（还没到判定断线的阈值）时，在后台先拨一条新的传输，拨通后才弃用旧传输，再在新传输上做续传握手。新传输拨不通时继续用旧传输，什么都不丢。旧传输必须在握手**之前**弃用：握手中报告的已收到字节数只有在旧传输不再交付数据之后才是确定的，否则握手之后到达的旧数据会被重复或丢失。
4. **重拨**：指数退避加抖动，每次重新解析 DNS。一个主机可以配置多个 endpoint（见[配置与状态文件](cli.md#配置与状态文件)）：拨号时先用上次成功的那个，失败再依次尝试其他的，并把剩余的时限分给它们，免得一个不回应的地址用光全部时间。
5. **有序结束**：主动结束的一方在最后一个字节之后发送结束帧，对方回一个结束帧，双方都看到对方的结束帧后才关闭传输，对方因此立即结束，不必等到租约过期。不能在发出结束帧后立即关闭：带着未读数据关闭的 TCP socket 会发送 RST，对方可能丢掉尚未读取的字节。传输断开时来不及交换结束帧的，对方等到租约过期（见[会话层覆盖不到的情况](#会话层覆盖不到的情况)）。
6. **避免队头阻塞**：交互（exec 的 stdio、端口转发、变更推送）、元数据（telefs 的小请求）、大块数据（telefs 的读写）分别走**不同的 TCP 连接**，这样一次大文件传输不会拖慢交互操作。每条连接都是一个独立的可恢复会话，各自重连和迁移。第一条连接建立 tele 会话，服务端在应答中给出一个随机的加入密钥；另外两条连接在 Hello 中带上会话 ID 和这个密钥加入同一个 tele 会话，服务端在它们上面提供同样的服务，tele 会话结束时一并关闭它们。加入失败的连接不影响会话：它的流量退回第一条连接。

**代价**：在丢包严重的链路上，TCP 的队头阻塞使表现不如基于 UDP 的方案，多条连接分担只能缓解。会话层不依赖 TCP 特有的语义，必要时可以把下层换成 QUIC 而不改动上层。

多路复用层（yamux）自己的保活和写超时要关闭或放宽：连接存活由会话层负责，yamux 不能在重连期间把会话关掉。

## 断线语义

| 业务 | 断线期间 | 重连后 | 超过会话租约 |
|---|---|---|---|
| Bash、hooks | 远端进程**继续运行**，输出缓存在服务端（有界，超出部分写入磁盘，见[进程与信号](exec.md#进程与信号)）；shim 阻塞等待 | 补发输出和退出状态 | 服务端在关闭会话之前，先对仍在运行的命令的进程组发送 SIGTERM，等待宽限期（`server.ExpireGrace`），然后关闭会话，剩下的进程被 SIGKILL；shim 返回错误 |
| Claude 的中断或超时（转发的信号，或 shim 被 SIGKILL 后的「结束进程组」请求） | 在会话中排队 | 送达远端并执行 | 远端已按租约规则结束进程组 |
| stdio MCP | 进程存活，消息排队 | 续传 | 进程结束，Claude 显示该 MCP 已断开 |
| telefs | 请求阻塞（类似 NFS 的 `hard`）；终端状态栏或日志显示「重连中」 | 续传 | 返回 `EIO` |
| 变更推送 | 服务端排队 | 续传；队列溢出时声明新 epoch，本地全量失效 | 全量失效 |
| 端口转发（HTTP/SSE MCP） | 转发的 TCP 流挂起，数据在会话层排队 | 续传 | 两端的 TCP 连接都被关闭 |

## 会话层覆盖不到的情况

- **tele server 进程重启或远端主机重启**：服务端内存中的会话丢失。telefs 按路径重新解析节点并全量失效（见[断线与恢复](telefs.md#断线与恢复)）；正在运行的命令失败；stdio MCP server 进程随之结束，Claude 显示该 MCP 已断开。
- **本地会话主进程崩溃**：Claude 随之退出，远端进程在租约到期后被清理。用 `tele <别名>[:<目录>] --resume` 恢复对话。
